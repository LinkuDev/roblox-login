Kiến trúc Node Fleet

Một order = một pool hàng nghìn record. Các node vật lý tự connect vào, claim record từ trên xuống, lấy user:pass, chạy flow, rồi ghi lại status của record (success / failed + lý do). Node cầm phần chạy và lật trạng thái record; SaaS giữ pool, sổ điểm và trừ tiền khi node report. Cả hệ chỉ là: giữ nguyên flow engine, tách một đường nối trong executor, và cho node claim/report qua một endpoint mỏng.

§0

Nguyên tắc cốt lõi

Invariant

Node = chạy flow + lật status record. Nó claim một record từ pool, lấy input, chạy Flow, rồi report kết quả — success, hoặc failed kèm lý do. Nó là thằng duy nhất biết kết quả nên nó phải là thằng đẩy record sang trạng thái cuối. Cái nó không giữ: logic point/order/billing, và credential DB thẳng.

SaaS = pool + sổ sách. Order sinh ra một pool record QUEUED. SaaS phát record khi node xin (claim), và khi node report thì SaaS ghi status + trừ điểm nếu thành công. Điểm/billing nằm sau lời gọi report, phía server — không rơi xuống node.

Nhờ ranh giới này, mở rộng ngang = bật thêm node (không đụng SaaS); và node "chạm DB" chỉ qua đúng hai thao tác claim / report — không phải toàn quyền vào Postgres.

§1

Topology & trust boundary

Node ở mạng khác, sau NAT, không tin cậy tuyệt đối. Nó kết nối ra ngoài tới một Pool API mỏng của SaaS và chỉ làm được hai việc: claim_next() lấy record, report() trả kết quả. Postgres (pool + sổ điểm) nằm hẳn phía trong; node không cầm creds DB, không có port DB nào phơi ra internet. Trừ điểm chạy server-side ngay khi report tới.

§2

Đường nối: tách executor.py thành claim · run · report

Đây là refactor mở khoá tất cả, và nó rẻ. Hôm nay modules/jobs/executor.py làm ba việc dính liền: đọc DB lấy input → chạy flow → ghi DB + trừ điểm. Cắt đúng hai vết: claim (server trả input) và report (server ghi status + bill). Pha giữa — run_service — không đổi một dòng, chỉ dịch xuống node.

§3

Vòng đời một record & cơ chế claim

Claim là "mượn có hạn". Node claim record (atomic, không hai node vớ trùng) rồi giữ một claim TTL. Có hai kết cục khác nhau, và phải phân biệt:

  • Fail nghiệp vụ (sai pass · account khoá · 2FA sai): node report failed + reason → record FAILED, terminal, không claim lại. Đúng như AutomationError hiện tại không retry.
  • Fail hạ tầng (node chết · WSS rớt · claim TTL hết): record tự nhả về QUEUED cho node khác, attempt++, tới ngưỡng mới bỏ.

§5

Giao thức Node ↔ SaaS (claim / report)

Envelope nhỏ, transport-agnostic — WSS hôm nay, đổi HTTP/NATS/gRPC sau chỉ là thay adapter. Đặt sau một port PoolLink giống cách BrowserSession giấu botasaurus. Node luôn là bên khởi xướng.

# envelope chung
{ "type": "claim", "msg_id": "...", "ts": 1725..., "payload": { ... } }

# Node → SaaS  (node khởi xướng)
hello        # auth(node_token) + capabilities[service] + max_slots + version
heartbeat    # free_slots, health, metrics — mỗi ~5s
claim        # xin tối đa n = free_slots record; SaaS trả records (atomic + TTL)
extend       # gia hạn claim TTL cho record đang chạy lâu
event        # started | step:{name,outcome} | needs_input(2fa / manual-captcha)
report       # {record_id, success, SessionArtifact} | {record_id, failed, error_code, reason}

# SaaS → Node  (đáp lại)
welcome      # chấp nhận + config (concurrency, poll interval)
records      # danh sách record trả cho một claim: credential, proxy, service_id, options, ttl
input        # đáp needs_input: mã 2FA / token captcha, đúng record đó
cancel       # huỷ record (order bị dừng) — node bỏ, nhả claim
drain        # ngừng claim mới, chạy nốt — để update/tắt node êm

needs_input: solver manual và bước 2FA thành một round-trip qua Pool API — node hỏi (event), server/admin trả (input), đúng record đó nhận lại. Thiết kế kênh hai chiều ngay để sau khỏi mổ lại.

§6

Fan-out hàng nghìn account — vì sao pull hợp hơn

  • Tự cân tải, không cần scheduler. Node khoẻ claim nhiều, node yếu claim ít — mỗi node chỉ xin đúng free_slots. Không có "bộ não" trung tâm phải theo dõi capacity từng node; đây là lý do pull đơn giản hơn push cho ca này.
  • Backpressure & fan-out là mặc định. Order 5.000 record đổ vào pool; node cứ rảnh là claim tiếp — tự trải khắp đàn, tốc độ thật = tổng throughput. Không cần "chia trước".
  • Claim phải atomic. Hai node không được vớ trùng record. Postgres: SELECT … FOR UPDATE SKIP LOCKED; hoặc Redis atomic pop. Đây là điểm sống-còn của mô hình pool.
  • Claim TTL = an toàn khi node chết. Reclaim record quá hạn về QUEUED. Node đang chạy lâu thì extend để khỏi bị giật mất.
  • Pacing chống rate-limit Roblox. Trần theo proxy/subnet, delay giữa các lần trên cùng IP — cài như filter lúc claim hoặc delay phía node.
  • Sticky theo account. Retry một account nên rơi về node/proxy cũ — claim ưu tiên record có affinity với node đang xin.
§7

Proxy

Proxy và port ProxyProvider.acquire(key=account) đã có — chỉ còn hỏi gán proxy ở đâu:

  • SaaS gán (khuyến nghị): claim trả kèm proxy sticky theo account. Pool tập trung, health & kế toán tập trung, retry giữ nguyên proxy. Node "ngu" — dễ vận hành.
  • Node-local pool: mỗi node có list proxy riêng theo region/mạng của nó (hợp residential gắn địa lý). Node tự chọn.
  • Lai: record mang proxy_policy = assigned | node_pool | direct; node resolve theo đó. Port hiện tại chạy được cả hai phía.
§8

Bảo mật & ranh giới tin cậy

  • Chỉ hai cửa. Node tác động DB đúng qua claim / report — không toàn quyền Postgres, không tự sửa điểm/đơn.
  • Danh tính node. Mỗi node một token (hoặc mTLS), xoay được; thu hồi là node mất quyền claim.
  • Credential là tài sản. user:pass chỉ đi trong WSS/TLS, node giữ trong RAM, xong record thì xoá — không ghi đĩa (hoặc mã hoá + TTL ngắn).
  • Blast radius nhỏ. Node chỉ thấy record đang claim; một node bị chiếm không lộ cả pool.
  • Kết quả nhạy cảm. Session cookie đi lên qua report; node ack xong nên xoá.

§10

Port & module mới cần thêm

  • domain/ports/pool_link.py — PoolLink: claim/report/event typed, transport-agnostic (WSS hôm nay).
  • providers/transport/ws_server.py · ws_client.py — adapter WSS cho hai đầu.
  • modules/nodes/ — pool_api (claim/report endpoint), pool_store (atomic claim + reclaim TTL), protocol (schema envelope), registry (heartbeat/health, cho dashboard).
  • node/ — runtime mới: NodeAgent (claim–run–report loop), slot pool, local buffer, reconnect. Dùng lại automation/runner.py nguyên vẹn.
  • Tách modules/jobs/executor.py → pool.py (claim_input + report_result); giữ execute_job làm đường local.
§11

Chốt trước khi code

Model pool–pull đã chốt theo hướng của bạn. Còn lại vài ngã rẽ — mình đề xuất sẵn, cái đầu là quan trọng nhất:

★ Câu mở chính

Node chạm pool bằng gì?

Endpoint mỏng của SaaS, hay cắm thẳng DB/Redis?

→ đề xuất endpoint claim/report (không creds DB trên node, billing server-side). Cắm thẳng chỉ khi node ở mạng riêng/VPN.

✓ Đã chốt

Pull-from-pool, không push

Node tự claim top-down; không dispatcher trung tâm.

→ tự cân tải, ít thành phần phải build.

Transport

WSS hay HTTP long-poll?

WSS cho bidirectional needs_input; HTTP đơn giản hơn nhưng phải poll.

→ đề xuất WSS sau port PoolLink, đổi sau chỉ là adapter.

Source of truth

Postgres, hay Redis là chính?

Cần claim nhanh + status bền + reclaim TTL.

→ đề xuất Postgres = truth (SKIP LOCKED), Redis chỉ là index tuỳ chọn.
